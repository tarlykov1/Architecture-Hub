# Бизнес-процессы Architecture Hub: паспорта, шаги и зависимости

**Рабочий пакет:** [PR #216](https://github.com/tarlykov1/Architecture-Hub/pull/216) · **метамодель:** [METAMODEL_V1.md](METAMODEL_V1.md).

## 1. Назначение и единый источник истины

Бизнес-процесс – это объект в существующем реестре `business_processes`, а не искусственно добавленная ИС. Его UUID неизменен, и им пользуются связи `process_systems`, карты бизнес-областей, сценарии обмена и потоковые атрибуты.

Новый **паспорт процесса** хранится в `business_process_passports` с ключом `process_id`. Это расширение существующего процесса: владелец, участники, ожидаемый результат, статус, родитель, номер ревизии. Существующие названия, категории и описания остаются в исходной таблице и изменяются через уже работающий редактор БП. Паспорта не копируют эти поля.

**Шаги** хранятся в `business_process_steps`. У каждого есть отдельный постоянный UUID, порядковый номер, название, описание, ответственный, вход и выход. Допустимы прямые ссылки на реальную ИС, её компонент, направленный технический поток и несколько атрибутов из общего справочника данных. Это ссылки на *определения*, не фактические персональные данные.

## 2. Правила архитектурной модели

| Факт | Правило | Проверка |
|---|---|---|
| Иерархия | Родительский процесс существует, принадлежит той же категории; цикл запрещён | API возвращает 422 |
| Владелец | Текстовый ответственный за БП; отдельная политика каталогов сотрудников может появиться позже | Изменение версии паспорта |
| Подсистема | Выбранный компонент обязательно принадлежит указанной ИС | API возвращает 422 |
| Технический поток | Выбирается из реестра `data_flows`; **не создаётся** вместе со шагом БП | Сохраняется исходный flow ID |
| Атрибуты | ID принадлежат `data_attributes`, без дубликатов и без хранения значений | API возвращает 422 |
| Порядок | Перестановка меняет `position`, но не UUID шагов и не технические потоки | Повторное открытие и E2E |
| Конкурентные правки | Изменение паспорта требует `expected_revision`; устаревшая версия даёт 409 | Защита от потери чужих правок |
| Удаление | Нельзя удалить действующие ИС, ВМ или поток, которые используются в шагах | API возвращает 409 |
| Аудит | Изменение паспорта и всех шагов – одна атомарная ревизия + запись истории | API и интеграционные тесты |

**Родительство не означает сетевое взаимодействие.** Участие двух ИС в одном БП не создаёт между ними технический поток. Подтверждённость сетевого трафика определяется отдельно от описания шага.

В модели BP можно описывать последовательность действий без полной нотации BPMN. Поддержка шлюзов/условий/параллельных веток будет отдельным расширением. Текущая «Схема» – другое отображение тех же шагов, а не ещё один редактор с копией данных.

## 3. Интерфейс

Открыть **Бизнес-процессы → нужная категория → Паспорт и шаги**. Внутри используются общий список шагов, простая вертикальная схема и правая панель свойств процесса. На мобильных экранах содержимое переходит в одну колонку, сохраняя поля и действия.

В режиме редактирования доступны владелец, участники, результат, статус, родитель, добавление/удаление/перестановка шагов, привязка ИС/компонента/потока/атрибутов. Закрытие с несохранёнными изменениями требует подтверждения. В случае конфликта версий пользователь должен обновить данные и повторить правку.

Из карточки можно скачать Markdown-описание *последней сохранённой* версии с идентификаторами и ссылками на зарегистрированные технические объекты.

### Матрицы

В бизнес-разделе доступен переключатель **Реестр процессов / Матрица зависимостей**. Матрица «БП × ИС» объединяет прежние прямые связи `process_systems` и ссылки шагов на ИС; «БП × Потоки» использует исключительно реальные `flow_id` шагов.

Матрица не придумывает отсутствующие потоки, не показывает статистику реального трафика и не считает отсутствие связи доказательством фактического отсутствия взаимодействия. Нажатие ячейки открывает тот же канонический паспорт процесса.

## 4. API и изменения БД

- `GET /api/business/process-passports` – список паспортов, включая процессы без заполненного паспорта (версия 0).
- `GET /api/business/process-passports/{process_id}` – описание процесса и его шаги.
- `PUT /api/business/process-passports/{process_id}` – атомарное сохранение паспорта и шагов с `expected_revision`, обязательной проверкой всех ID.
- Права действующего слоя `business` (просмотр/изменение) применяются через серверный RBAC, а не только скрытие кнопок.

Миграция `0020_business_process_passports` создаёт две новые таблицы и индексы, не изменяя старые строки `business_processes`, `process_systems` или `data_flows`. Миграционные тесты проверяют populated SQLite и случай, когда ORM `create_all` уже успел создать новые таблицы.

**Важно:** наличие ORM-таблиц и успешный CI **не означают**, что на тестовом VPS продвижена Alembic-ревизия. Известная задача [#215](https://github.com/tarlykov1/Architecture-Hub/issues/215) требует проверки и согласования серверной схемы на резервной копии перед изменениями флага миграций. Не выполнять безусловный `stamp head` или операцию `upgrade` на живой SQLite.

## 5. Критерии приёмки

1. Процесс создан и сохранён в прежнем реестре, без одноимённого объекта `objects`.
2. Паспорт сохраняется и открывается по тому же `process_id`, даже если пользователь закрывает вкладку или входит из другого браузера.
3. Вложенность циклов и неверные связи отклоняются, старые записи не повреждаются.
4. Добавление, перестановка, редактирование и удаление шагов сохраняют UUID всех оставшихся шагов.
5. Реальный поток остаётся тем же после изменения шага; удаление потока, используемого в БП, блокируется.
6. Ревизии растут, одновременно открытые редакторы не затирают чужую версию.
7. Матрицы, карточка, схема и Markdown выгрузка отображают одни и те же факты и имена.
8. Chromium E2E покрывает desktop/mobile, серверную запись, reload, 409 и скачивание.
9. Backend миграция на **копии** заполненной БД проходит с проверкой целостности, схема на сервере проверяется отдельно.

После этого API и UI можно считать готовыми для внутреннего использования в тестовой версии; не следует утверждать, что данные автоматически подтверждены владельцами процессов.

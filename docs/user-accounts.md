# Персональные учётные записи и роли в Architecture Hub

Начиная с версии после PR про вход по паролю, можно завести **отдельные учётные записи** сотрудников. Общий пароль администратора и служебные ключи временно сохраняются для перехода, поэтому существующий доступ не блокируется.

## Первый вход и создание пользователей

1. Откройте тестовый стенд `https://test.web-tie.ru/`.
2. Войдите **по прежнему общему паролю**, оставив поле «Логин» пустым.
3. Нажмите **«Пользователи»** в правой части шапки.
4. Создайте персональную запись: латинский логин (3–64 символа), отображаемое имя, роль и индивидуальный пароль (от 12 символов).
5. Создайте прежде всего **отдельного администратора** и убедитесь, что он может войти.
6. Далее создавайте архитекторов, инженеров, специалистов ИБ и наблюдателей.
7. Пользователь вводит **свой логин и пароль**. Он может сменить собственный пароль, а администратор – сбросить пароль через управление пользователями.

Пароли не отображаются в списке; в БД хранится лишь PBKDF2-SHA256 хэш с солью. Смены пароля и ролей, а также блокировка учётной записи сразу отзывают её старые сессии (сервер сверяет session_version с записью при каждом запросе). Сессии действуют до 8 часов; ручной выход удаляет токен из вкладки.

## Роли

| Роль | Основные возможности |
| --- | --- |
| Администратор (`admin`) | Управление учётными записями, полные права на архитектуру |
| Архитектор (`architect`) | Редактирование систем, компонентов и потоков; сети – просмотр |
| Инженер (`engineer`) | Редактирование инфраструктуры/сетей; просмотр схем и потоков |
| Информационная безопасность (`security`) | Редактирование сетевого реестра, просмотр зависимых систем |
| Владелец процесса (`business_owner`) | Редактирование бизнес-процессов, просмотр систем |
| Наблюдатель (`viewer`) | Просмотр доступных систем, процессов, схем и инцидентов без записи |

Права проверяются **сервером**, а не только скрытием кнопок. Недоступные каталоги в главном экране отображаются пустыми и не ломают авторизацию. Для остальных экранов ещё предстоит отдельная UX-доработка отображения разрешений и полей редактирования.

## Защита от потери доступа

- Приложение не позволяет заблокировать или понизить роль **последнего активного персонального администратора**.
- Общий пароль, настроенный в `/etc/architecture-hub.env`, пока остаётся аварийным способом входа. **Не удаляйте его сейчас**.
- После создания персонального администратора, проверки входа, теста восстановления и аудита можно отдельно запланировать отказ от общего пароля.
- Предыдущие API-ключи сохраняются для CI, интеграций и служебных операций.

## База данных и развёртывание

Добавляется одна таблица `auth_users` и Alembic-миграция `0010_auth_users`. В тестовом стенде FastAPI использует `Base.metadata.create_all` при старте; развёртывание не требует ручной миграции и не переписывает существующие таблицы. На сервере работает резервное копирование SQLite до релиза. Не включайте автоматически все Alembic-миграции на существующей БД без проверки текущей ревизии.

Перед добавлением пользователей должна быть настроена пара `ARCH_HUB_LOGIN_PASSWORD_HASH` + `ARCH_HUB_SESSION_SECRET` (она уже используется входом по паролю).

## Ограничения этой стадии

Это персональные аккаунты и RBAC для тестового этапа, но **не SSO**. Отсутствуют MFA, приглашения, сброс пароля по электронной почте, централизованная блокировка по IP и cookie-сессии HttpOnly. Для промышленного использования рекомендуются внешняя идентификация/SSO, MFA, расширенный аудит действий, отдельные права на конкретные объекты и ограничение запросов входа на reverse-proxy.

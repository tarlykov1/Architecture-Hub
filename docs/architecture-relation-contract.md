# P0 – контракт логических связей информационных систем

Это **первый реализованный фрагмент** целевой метамодели ArchHub, а не полноценная поддержка ArchiMate/C4.

## Реальные источники данных

`/api/objects` содержит логические архитектурные объекты. В `/api/relations` сохраняются **только направленные логические отношения двух ИС** (`kind=system`). Техническая передача данных между компонентами, протоколы, порты и средства защиты моделируются через `/api/flows` и связанные технические API.

`GET /api/metamodel/relation-types` возвращает документированный набор допустимых логических типов:
- `integrates_with` – логическая интеграционная зависимость (не подтверждает транспорт).
- `depends_on` – ИС-источник зависит от ИС-получателя.
- `data_flow` – исторический вид связи двух ИС; **deprecated**, он не должен использоваться как доказательство технического потока.

Новая линия в редакторе общей схемы ИС создаёт `integrates_with`, а не `data_flow`. Ранее записанный `data_flow` остаётся виден с пометкой устаревшего типа.

## Проверка записи

`POST /api/relations`:
1. Требует авторизации с правом записи в разделе `systems`.
2. Отклоняет самосвязи, неизвестные объекты, неизвестные типы и типы конечных объектов, отличные от `system`, кодом 422.
3. Сохраняет дополнительные действующие ограничения CMDB `CmdbRelationshipRule`.
4. Для уже существующей пары `source_id`, `target_id`, `kind` возвращает 409; обратное направление считается отдельной связью.
5. Не изменяет идентификаторы или типы ранее записанных отношений.

Проверка дублирования на этом этапе прикладная (read-before-write). **Параллельная запись двух одинаковых запросов ещё требует отдельной уникальной DB-ограничивающей миграции и безопасного плана удаления исторических дублей**.

## Инвентаризация без изменений БД

`GET /api/metamodel/relation-audit` – read-only отчёт для миграционного анализа:
- число объектов по `kind`;
- число отношений по типу;
- количество неизвестных типов, отношений с неправильными конечными объектами, потерянных ссылок, повторов одной направленной связи и legacy `data_flow`;
- максимум 20 ID проблемных отношений для дальнейшего анализа.

Отчёт **ничего не исправляет и не удаляет**. Имена, тексты паспортов и технические данные в примерах не выдаются; доступ регулируется чтением ИС.

## Проверки

- API тесты с ролями admin/viewer и guest.
- Проверка 422, 409, направления, отсутствия дублей и чтения исторических связей.
- Проверка чистой функции классификации legacy и неповреждения источников данных.
- Full CI/Playwright обязателен перед объединением.

## Следующий шаг

Перед миграцией к полноценной типизированной модели связей необходимо собрать результат `relation-audit` на **копии** существующей БД, утвердить соответствие типов `ArchitectureObject.kind` каноническим сущностям и нормализовать отношения по бизнес-процессам, данным и инфраструктуре отдельно, не превращая все отношения в одно `relations`.

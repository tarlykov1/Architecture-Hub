# Технологический стек, версии и проверка через разрешённый мониторинг

## Задача

При появлении сведений об уязвимости (например, для определённой версии
PostgreSQL, OpenSSL или Java) быстро выяснить **в каких ИС и на каких
компонентах** она потенциально присутствует, какой версии ПО принадлежит
запись, из какой среды она взята и **когда это проверяли**.

Наличие программной платформы в паспорте не означает наличие уязвимости.
Отсутствие мониторинга не означает, что ИС недоступна или защищена.

## Две разные сущности

- **Технология** (`system_technologies`): заявленное ПО, версия, категория,
  среда (PROD / TEST / DEV / STAGE), конкретный компонент ИС либо ИС в целом,
  жизненный цикл, дата окончания поддержки, поставщик, источник сведений и
  степень подтверждения. Две версии в разных контурах не объединяются.
- **Наблюдение** (`system_technology_observations`): полученные от внешнего
  *разрешённого* мониторинга версия, доступность, UTC-время измерения и
  источник. Наблюдения записываются отдельно и не переписывают паспорт.
  Последняя запись видна в паспорте и общем реестре. Старые наблюдения
  сохраняются до явного удаления технологии.

Паспорт ИС – вкладка «Технологический стек». Реестр всех установок –
**Системы → Реестр технологий**. Искать можно по системе, компоненту,
названию технологии или строке версии, с фильтрами среды/категории.

## Политика проверок

На текущем этапе Architecture Hub **не выполняет ICMP ping, DNS-запросы,
сканирование IP/портов, SSH, WMI, HTTP-запросы к пользовательским адресам**
и не пытается определить версии по открытым портам.

Имеющиеся интеграции мониторинга – пока каталог ссылок и привязок, а не
подключение с API-токенами. Поэтому реальную доступность и обнаруженную
версию можно получить лишь от явно настроенного клиента/адаптера мониторинга.

Адаптер передаёт уже полученную телеметрию:

```
POST /api/systems/{system_id}/technologies/{technology_id}/observations
{
  "source_id": "<UUID зарегистрированного источника>",
  "observed_at": "2026-11-18T10:15:00+03:00",
  "observed_version": "16.3",
  "reachable": true,
  "notes": "Проверка из системы мониторинга"
}
```

Сервер принимает её только когда:
1. вызов авторизован как изменение реестра ИС;
2. источник существует, включён и связан с данной ИС или конкретным
   компонентом отношением `monitors` (а не просто `visualizes`);
3. технология действительно относится к этой ИС;
4. временная метка с часовым поясом, не из будущего;
5. задан хотя бы один показатель (доступность или наблюдаемая версия).

`GET /api/systems/{id}/technology-observations` показывает записи.
`GET /api/technology-inventory` формирует общий поисковый реестр
с расхождением версий, признаком завершения поддержки и временем последнего
отчёта. Данные показываются как **полученные от источника**, без
необоснованного заявления «проверено самим Hub».

## Разрешения и безопасность

- Чтение реестра – существующее разрешение `systems:read`.
- Запись технологий и наблюдений – `systems:write` (серверный RBAC).
- Подмена `source_id` без связи с целевой ИС/компонентом → `422`.
- Отключённые источники и источники без `monitors` не могут отчитываться.
- URL источника не принимается как произвольная цель пинга/сканирования.
- Изменения технологического состава журналируются в архитектурном аудите.
- Отсутствующая или устаревшая проверка показана явно.
- Поиск CVE и автоматическое сопоставление уязвимостей в этой итерации
  **не реализованы**. Не следует выводить «уязвимо» лишь из совпадения имени.

## База данных

Аддитивные миграции:
- `0016_system_technologies`
- `0017_technology_observations`

Ревизии не переклассифицируют и не удаляют старые ИС, ВМ, VLAN или потоки.
Тест `backend/tests/test_technology_migrations.py` проверяет обновление
изолированной заполненной SQLite.
Тест `test_system_technology_inventory.py` проверяет принадлежность
компонентов, разные среды/версии, права, контроль источника и сохранность
проверок. UI: `frontend/e2e/audit-system-technology-inventory.spec.ts`.

## Следующий отдельный этап – настоящий коннектор

Нужен явный согласованный перечень ИС и атрибутов проверки, read-only API
аккаунт Zabbix/Prometheus/Grafana, ограничения запросов и разрешённый маршрут
к серверу мониторинга. Коннектор должен выбирать только известные
`external_ref` (host/item ID), а не произвольные IP/URL, хранить токены
в секретах и фиксировать ошибки/источник. Лишь после такой настройки можно
добавлять действие «Запросить проверку» и плановые сверки. До этого кнопка
активного пинга не показывается, чтобы не создавать ложного ощущения контроля.

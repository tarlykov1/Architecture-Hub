# ArchHub: метамодель v1, отношения и инварианты

Статус: **целевая спецификация**. Документ предназначен для инженерной реализации, QA и миграций; не заявляет, что все классы существуют в текущей SQLite. Связан с [целевой методологией](ARCHITECTURE_VISION.md).

## 1. Разделение: факт, утверждение, представление

Три разных уровня:

1. **Entity** — канонический объект предприятия с неизменяемым `id`, типом и жизненным циклом.
2. **Relation / Fact** — явно зафиксированная связь между сущностями, имеющая тип, направление, источники, проверку и (при необходимости) временные границы.
3. **View / ViewRegion** — проекция данных на холст. Прямоугольники, цвета, координаты и настроенные видимые участники **не меняют** Entity/Relation.

Один и тот же объект можно использовать в нескольких представлениях. Один факт может быть явно зарегистрирован, вычислен как производный или только предположен; это должно быть видно API и UI.

Для каждого объекта и отношения — `id`, `created_at`, `updated_at`, `source`, `provenance`, `verification`, `revision`; для важной архитектуры — `owner`. UI должен отличать подтверждённое от наблюдаемого и предполагаемого.

## 2. Базовые классы предметной области

| Тип | Определение | Ключевые поля | Источник |
|---|---|---|---|
| BusinessCapability | Способность организации осуществлять деятельность | name, parent_id, owner, criticality | бизнес-владелец |
| BusinessProcess | Процесс/сценарий достижения результата | name, category/capability, owner, status | процессный реестр |
| OrganizationUnit | Подразделение, владелец или потребитель | name, parent_id, responsibility | орг. справочник |
| ITService | Услуга для потребителя и её обещание | name, owner, criticality, SLA reference | ITSM |
| InformationSystem | Логическая информационная система как объект архитектуры | name, description, owner, lifecycle, criticality, fit | архитектурный реестр |
| ApplicationComponent | Развёртываемый/логический компонент ИС | name, kind, owner, environment | команда приложения |
| VM | Виртуальная машина как вычислительный ресурс | name, platform, environment, lifecycle | виртуализация |
| NetworkInterface | Интерфейс устройства/ВМ | item_id, name, MAC, IP assignments | сетевой источник |
| NetworkZone | Административная/защитная зона | name, purpose, security level | ИБ / сеть |
| VRF | Независимый домен маршрутизации / таблица маршрутов | name, RD, route targets if known | сеть |
| VLAN | L2-домен в определённой области видимости | name, VLAN ID, scope, status | сеть |
| IPPrefix | IP-подсеть с VRF-контекстом | prefix, VRF (or global), status | IPAM |
| IntegrationFlow | Зарегистрированная направленная передача от конкретного источника к конкретному получателю | source_id, target_id, transport, port, protection, status | архитектура интеграций |
| DataAttribute | Канонический элемент данных | code, name, type, sensitivity | каталог данных |
| FlowDataUse | Использование атрибута в потоке и конкретном процессе/получателе | flow_id, attribute_id, process_id, consumer_id, purpose | интеграционная спецификация |
| ArchitectureView | Настройка перспективы, уровня, фильтров и раскладки | viewpoint_type, scope, layout, layers, owner | архитекторы |
| ViewRegion | Нарисованная/настроенная область на конкретной схеме | view_id, group_id, geometry, opacity, color, displayed_members | UI |

**Не внедрять весь список одной миграцией.** Части уже существуют под именами `objects`, `infrastructure_items`, `flows`, `business_*`, `network_segments`, `network_interfaces`, `diagrams`, `cmdb_records`. Сначала составить таблицу соответствий существующих идентификаторов и предметных классов; миграции делать аддитивно.

### Семантические нюансы

- BusinessCapability отличается от BusinessProcess: capability — **что** организация умеет, process — **как** выполняется.
- InformationSystem может быть связана с несколькими бизнес-возможностями, процессами, владельцами-потребителями, компонентами и IT-сервисами.
- ApplicationComponent и VM — разные классы. Система может содержать десятки компонентов, часть из которых размещена на нескольких ВМ.
- C4 Container — логическая исполняемая/хранилищная единица, **не тождественна** ни VRF/VLAN, ни VM. При необходимости ввести отдельный логический DeploymentUnit, не переименовывать VM в «контейнер C4».
- VLAN — L2; VRF — L3 routing context; NetworkZone — граница/классификация безопасности; IPPrefix — адресный ресурс. Их нельзя делать подвидами друг друга.
- В NetBox префикс/адрес имеет VRF-контекст; совпадающие CIDR в разных VRF допустимы. Идентичность сетевого объекта не должна определяться одним текстовым CIDR.

## 3. Разрешённые отношения

Примеры `relation_type` (наименование — предложение для стабильного API):

| Relation | Source → Target | Смысл/ограничения |
|---|---|---|
| `capability_parent` | Capability → Capability | иерархия без циклов |
| `process_realizes_capability` | Process → Capability | поддерживает бизнес-функцию, не передаёт данные |
| `system_supports_process` | IS → Process | участие, роль обязательно: owner/producer/consumer/support |
| `system_supports_capability` | IS → Capability | прямое высказывание, не обязательно выводить из Process |
| `org_owns_system` | Org → IS | тип ответственности business/technical/application; допускается история |
| `service_implemented_by_system` | ITService → IS | service-to-application связь |
| `system_contains_component` | IS → Component | логическая принадлежность |
| `component_deployed_on` | Component → VM | физическое/виртуальное размещение, many-to-many |
| `vm_has_interface` | VM → Interface | владелец интерфейса |
| `interface_in_vlan` | Interface → VLAN | в рамках конкретного scope; явная связь |
| `interface_in_zone` | Interface → Zone | политика/сегмент, явная связь |
| `ip_prefix_in_vrf` | Prefix → VRF | учёт контекста маршрутизации; nullable = global |
| `flow_from` | IntegrationFlow → Component | ровно один источник |
| `flow_to` | IntegrationFlow → Component | ровно один получатель |
| `flow_attribute_use` | IntegrationFlow ↔ DataAttribute + Process | роль, получатель, назначение, статус и направление |
| `derived_dependency` | любая допустимая пара | создаётся query/analysis, **не записывается как подтверждённый первичный факт** |

Для каждой relation нужны `allowed_source_types`, `allowed_target_types`, `direction`, `cardinality`, `required_fields`, `evidence_required`, `traversal_policy`.

**Валидация по контракту:**
- нельзя создать `component_deployed_on` между двумя ИС;
- нельзя создать `interface_in_vlan` без существующего Interface и VLAN;
- нельзя связать два VM без осмысленного `relation_type` и утверждать, что возникла техническая передача;
- изменение source/target IntegrationFlow требует подтверждения, сохраняет flow ID и формирует diff;
- одна стрелка на диаграмме может визуализировать несколько независимых flows: они не должны слиться в одну запись.

## 4. Поток данных и бизнес-контекст

Сценарий: ЗУП → ЕИБД передаёт пакет атрибутов сотрудника. По одному бизнес-процессу используются ФИО и подразделение, по другому — табельный номер и статус доступа.

**Не создавать два выдуманных физических соединения только потому, что есть два процесса.**

- `IntegrationFlow` описывает существующее техническое взаимодействие (компоненты, транспорт, данные, частота, защита, маршрут, верификация).
- `FlowDataUse` описывает, **какой атрибут** в **каком бизнес-процессе**, каким потребителем, для какой цели используется. У одного flow много FlowDataUse.
- Каталог показывает полный зарегистрированный набор атрибутов потока; контекст БП показывает его подмножество.
- Источник, трансформация и потребитель данных связаны трассируемой цепочкой (lineage) с явным преобразованием и доказательствами при наличии.
- Служебные данные/PII должны иметь класс чувствительности, без публикации реального значения в каталоге.

При отсутствии доказательств о фактической передаче набор помечается `declared` или `assumed`, а не `observed` или `verified`.

## 5. Сетевой контекст и маршрут

Иерархии и принадлежности должны быть точными:

- `VRF`: отдельное пространство L3-маршрутизации;
- `VLAN`: L2-домен, VLAN ID уникален только в определённом scope;
- `IPPrefix`: CIDR + VRF как часть контекста уникальности;
- `Interface`: адреса, VLAN, зона и VM/устройство;
- `NetworkZone`: классификация и контроль; не обязательно 1:1 с VLAN или VRF;
- `NetworkPath`: последовательность **заявленных/проверенных** переходов (zone, firewall, proxy, NAT, gateway, VRF); для каждой ступени свой источник/верификация.

Интерфейс **не должен** сообщать «поток проходит через межсетевой экран X» только по двум IP-адресам либо общему VRF. Возможные статусы маршрута: `unknown`, `declared`, `observed`, `verified`, `blocked`; только фактически подтверждённый маршрут является подтверждённым.

## 6. Данные, происхождение и качество

Для сущностей и особо для связей:

```text
entity_id / relation_id
canonical_type / relation_type
source_system + source_record_id + import_batch_id
origin = manual | import | discovery | derived
claim_status = assumed | declared | observed | verified | disputed | stale
observed_at / verified_at / effective_from / effective_to
verified_by / owner / evidence_uri
revision / updated_at
```

`evidence_uri` может ссылаться на документы, CMDB, тикет, сетевую конфигурацию, результат обнаружения; не хранить секреты и конфиденциальные значения в общедоступных полях.

**Отдельные показатели качества:**
- Completeness = доля заполненных обязательных полей с весами;
- Verified coverage = доля релевантных утверждений с актуальным подтверждением;
- Freshness = насколько сведения соответствуют требуемому сроку актуализации;
- Conflicts = количество несогласованных свидетельств по одному атрибуту.

Пример: «у ИС 95% заполнения, но подтверждено 35% критичных связей» — допустимо, нельзя сворачивать в одно зелёное «качество 95%».

## 7. Представления и слои

`ArchitectureView` не хранит копию объектов. Хранит `viewpoint_type`, `scope`, `visible_entity_ids` (или запрос), `enabled_layers`, `filters`, `layout_ref`, `legend`, `version`, `owner`.

`ViewRegion` хранит:
- идентификатор существующей категории/зоны (`group_id`);
- принадлежащие **визуальному представлению** system/component IDs;
- x, y, width, height, opacity, color, z-order;
- идентификатор view, в рамках которого сохранена область.

Прямоугольники могут перекрываться и их членство может различаться на разных viewpoints. **Визуальное членство не меняет фактических `system_supports_process` или `interface_in_vlan`.**

Сохранять layout отдельно от viewpoint и отдельно от технических связей; переключение бизнес/сети/данные не должно передвигать VM. Изменить источник связи физического потока можно только в режиме изменения фактов с preview.

Текущая `architecture_layer_regions` — **промежуточная реализация**, привязанная к `group_key`; перед многосхемностью потребуется привязка `view_id` и управление версионированием/конкурентными изменениями.

## 8. Изменения и история

Все значимые изменения проходят:
`draft → preview/validation → reviewer (при необходимости) → commit → audit`.

- Diff содержит `before/after` по каждому полю и затрагиваемые отношения.
- Ошибка между несколькими операциями не создаёт наполовину сохранённую модель: транзакция.
- Ролевая матрица проверяется backend, а не только UI.
- Любое массовое изменение требует причины и preview.
- Отмена layout-черновика **не** затрагивает реестр.
- Секреты никогда не попадают в аудит или клиентские диагностические файлы.

## 9. Техническое внедрение без разрушения БД

Перед созданием новых таблиц подготовить однократное соответствие старых типов:

| Существующая сущность | Целевая трактовка | Риск |
|---|---|---|
| `ArchitectureObject` | InformationSystem (при kind=system) | иные kind требуют сверки |
| `InfrastructureItem` | компонент / VM по kind | существующие атрибуты могут смешивать размещение и описание |
| `Flow` | IntegrationFlow | сохранение ID и связей с данными |
| `ProcessSystem` | явная поддержка БП | роль, достоверность и источник могут отсутствовать |
| `NetworkSegment` | VRF/VLAN/Zone/Prefix по kind | разные семантики сейчас объединены |
| `NetworkInterface` | Interface | возможны неполные IP/VRF/VLAN |
| `Diagram` и `BoardLayout` | ArchitectureView/Layout | координаты не должны стать источником данных |
| `CmdbRecord` | метаданные CI | синхронизация с каноническими объектами |
| `ArchitectureLayerRegion` | временная реализация ViewRegion | нужна привязка к view и разделение визуального/фактического состава |

Нельзя автоматически мигрировать объект `kind=vm` в иной тип, если его смысл не подтверждён. Создавать mapping report и dry-run с обнаружением конфликтов.

## 10. Минимальные автоматические проверки

- Не существует двух канонических сущностей с одним внешним source+record ID в одном namespace.
- Запрещены недопустимые пары для typed relations и циклы в иерархиях.
- Change request сохраняет идентификаторы существующих flow при переносе конечных точек.
- Выделение слоя/смена цвета/геометрии не создаёт бизнес/сеть/flow relation.
- Перенос VM между геометрическими рамками не перемещает реальный NIC в другой VLAN.
- Параллельные потоки не теряют отдельные наборы данных и атрибутов.
- Вывод dependency graph содержит путь зависимостей и quality metadata.
- Viewer не может записать даже прямым API-вызовом.
- Предположение и устаревшие данные маркированы в UI, export и API.

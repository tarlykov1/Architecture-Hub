# Договоры, лицензии и поддержка ИС

## Назначение

Паспорт информационной системы включает самостоятельный раздел «Договоры и лицензии».
Договорные сведения **не являются техническими связями, NIC, VLAN, потоками данных
или процессами** и не создают новых ИС в архитектурном реестре.

- `system_contracts` – договоры на покупку, подписку, поддержку, разработку/внедрение
  и другие формы обслуживания. Одна ИС может иметь несколько договоров.
- `system_licenses` – лицензируемые продукты/редакции, их тип, количество, сроки;
  несколько строк могут относиться к одному договору.
- Договор хранит вендора, подрядчика, номер, даты начала/окончания и продления,
  автопродление, период уведомления, уровень/окно поддержки, SLA реакции (часы),
  SLA доступности (%), контакт и заметки.
- Лицензия имеет отдельный срок. Даты окончания договора, продления и окончания
  лицензии **не являются одной и той же датой**.

## Безопасность и ограничения

- Используются существующие роли чтения/записи реестра ИС (`systems`).
  Серверная авторизация обязательна. Роль viewer может читать, но не редактировать.
- Лицензионные ключи, пароли, договорные сканы и конфиденциальные вложения
  в этом MVP не сохраняются.
- Договор нельзя удалить, пока есть связанные лицензии (`409`).
  Для связи лицензии с договором сервер проверяет, что обе записи одной ИС (`422`).
- Удаление ИС с договорными данными блокируется (`409`), чтобы не терять
  юридически значимые сведения.
- Операции создания, изменения и удаления журналируются транзакционно.
- Обновления сохраняют существующие UUID записей; автоматической дедупликации
  или конвертации из текстовых примечаний старых паспортов нет.

## API

```
GET  /api/systems/{system_id}/contracts
POST /api/systems/{system_id}/contracts
PUT  /api/systems/{system_id}/contracts/{contract_id}
DELETE /api/systems/{system_id}/contracts/{contract_id}

GET  /api/systems/{system_id}/licenses
POST /api/systems/{system_id}/licenses
PUT  /api/systems/{system_id}/licenses/{license_id}
DELETE /api/systems/{system_id}/licenses/{license_id}
```

Ошибки валидации дат, SLA, количества и типа лицензии возвращают `422`.
Пустой набор возвращается пустым списком, не демонстрационными данными.

## Изменение схемы

Аддитивная Alembic-ревизия `0015_system_commercial` создаёт две таблицы.
Действующие записи `objects`, `business_processes`, `infrastructure_items`
и технических связей не меняются. Для миграции существующей БД требуется
сначала сделать и проверить резервную копию, затем выполнить
`alembic upgrade head`. Откат, удаляющий договорные записи, намеренно запрещён.

Проверка: `backend/tests/test_system_commercial_migration.py` моделирует
обновление старой заполненной SQLite, а `test_system_commercial.py` проверяет
API и сохранность идентификаторов. Новый браузерный сценарий:
`frontend/e2e/audit-system-commercial.spec.ts`.

## Дальнейшие расширения (не включены в итерацию)

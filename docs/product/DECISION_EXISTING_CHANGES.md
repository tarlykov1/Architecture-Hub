# AH-05 – проектирование изменений действующей архитектуры

**Реализация:** [PR #219](https://github.com/tarlykov1/Architecture-Hub/pull/219) · **область:** технические решения, сравнение «было → станет», согласование.

## Цель

Архитектор должен проектировать изменения прямо в актуальном Architecture Hub, используя действующие ИС, компоненты и потоки, а не рисуя второй несвязанный документ.

Внутри одного технического решения доступны три вида изменений:

- **Создание** новых проектируемых ВМ и направленных потоков.
- **Изменение** параметров уже зарегистрированных ВМ/серверов и технических потоков с сохранением их ID.
- **Планируемое удаление** существующих ВМ и потоков, с контролем зависимостей и явным выделением на схеме.

Все три вида отображаются в представлениях решения и входят в одну ревизию согласования. Ни один вид не изменяет действующий реестр при редактировании, отправке или публикации документа.

## Модель и безопасность

Ранее существующие таблицы `technical_decisions` и `data_flows` не изменяются. Изменения существующих объектов хранятся в новой **добавочной** таблице `technical_decision_change_plans` с полями `decision_id` (FK) и `changes` (JSON), миграция `0021_technical_decision_change_plans`.

Это сделано сознательно: на тестовом VPS есть [#215](https://github.com/tarlykov1/Architecture-Hub/issues/215), где миграции Alembic не включены, а ORM может создавать только новые таблицы. При развёртывании новой версии старая таблица технических решений остаётся совместимой.

Каждый пункт `existing_changes` включает:

| Поле | Смысл |
|---|---|
| `id` | Канонический ID действующего VM или flow |
| `kind` | `vm` или `flow` |
| `action` | `update` или `remove` |
| `fields` | Только изменяемые свойства, выбранные пользователем |
| `before` | **Серверный снимок** исходного зарегистрированного объекта |
| `after` | Серверно вычисленная целевая модель или `null` при удалении |

Отправленное клиентом `before` **не принимается за источник истины**. Backend независимо считывает каноническую запись. Если исходные параметры с момента составления проекта изменились, согласование блокируется с `409`: изменение не может молча получить подписи для уже неактуальной архитектуры.

### Ограничения согласованности

- Нельзя планировать изменение ВМ другой ИС; изменение потока допустимо только при наличии хотя бы одного конца в ИС решения.
- Порт, тип ВМ, статусы проверки, ID концов потока проверяются на сервере.
- Нельзя дважды запланировать противоположные действия для одного объекта.
- Удаление ВМ требует предварительно пометить к удалению **все** связанные зарегистрированные потоки. Нельзя оставить новый проектный поток к удаляемой ВМ.
- Нельзя запланировать удаление ВМ с действующими дочерними компонентами, NIC или записями технологии: поддержка этих изменений должна быть добавлена позже.
- Отклоняется попытка планировать отсутствие изменения как отдельное действие.
- `expected_revision` защищает от перезаписи чужих правок; локальный Undo/Redo тоже записывает новую серверную ревизию.
- Совместимость: старый клиент, не отправивший `existing_changes`, не удаляет сохранённые изменения.
- Комментарии могут относиться к существующим ВМ/потокам, затронутым проектом, с проверкой ID.

## Поведение пользователя

**Технические решения → создать/открыть черновик → Изменения.**

Там есть список всех запланированных операций и сравнение свойств. Можно выбрать действующую ВМ или поток, изменить параметры или отметить к удалению. В схеме существующие узлы и стрелки, затронутые решением, отмечаются иначе, чем новые проектируемые узлы.

Техническое решение может содержать **только изменения существующих объектов**, без добавления новой ВМ. Такой черновик можно отправить на согласование.

Для сохранённого проекта доступны версии, изменения по полям, история отмены/повтора и Markdown-выгрузка с описанием согласований.

### Статусы

`draft → in_review → approved → published`; при замечаниях возвращается `changes_requested`.

**Опубликовано** значит «согласованный документ», а **не** «изменённая инфраструктура». Отдельный механизм регистрации фактического внедрения, сверки с реальным контуром и подтверждения его службами остаётся задачей AH-05-08/09. Модельный diff не является доказательством внедрения.

## Проверки и приёмка

- `backend/tests/test_existing_decision_changes.py`: server snapshots, security scope, допустимые поля и маршруты, зависимости, stale revisions, неизменность реальных VM/flow, комментарии и согласование только предложенных изменений.
- `backend/tests/test_decision_change_plan_migration.py`: миграция 0021 на заполненной SQLite и отсутствие потерь старых решений.
- `frontend/e2e/decision-existing-changes.spec.ts`: реальное изменение ВМ/потока через UI, сохранение после reload, инспектор, схематическая подсветка, Undo/Redo, отправка решения, запланированное удаление и Markdown export.
- Все проверки базового редактора, обратных потоков, бизнес-процессов и мобильного режима из существующей регрессии.

**Условие релиза:** успешные backend tests, TypeScript build, Playwright Chromium, Docker/PowerShell, контролируемая выкладка в `main` и Live QA опубликованного сайта. Без зелёной приёмки новый код остаётся в PR.

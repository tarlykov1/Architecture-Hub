# ArchHub: сквозные пользовательские и методологические проверки

Эти сценарии должны служить стандартом качества для разработки. Это **target acceptance**, не утверждение, что сценарии уже проходят. Конкретные сущности пилотного контура создаются в отдельной тестовой БД и именуются `QA-WORK-*`.

## A. Одна сущность на все представления

**AH-ACC-001 — единая ИС**

Дано: одна IS «1С ЗУП» с каноническим ID и 4 компонентами.  
Когда: открыть реестр, паспорт, бизнес-слой, слой потоков, сетевой слой, прямую ссылку и перезагрузить.  
Тогда: везде тот же ID и та же карточка; изменение имени отражается во всех представлениях без копирования объекта.

**AH-ACC-002 — переключение областей**

Дано: ИС на постоянных координатах и две полупрозрачные области (бизнес/сеть).  
Когда: переключить, наложить, перекрасить, передвинуть, сохранить, отменить, открыть с другого пользователя.  
Тогда: ID и координаты ИС/ВМ неизменны; состав/геометрия областей воспроизводятся; конфликт изменения явно выявляется.

**AH-ACC-003 — область ≠ реальная принадлежность**

Дано: одна VM визуально пересекает нарисованный VLAN.  
Когда: изменить размеры или переместить область.  
Тогда: `NetworkInterface.vlan_id`, `vrf_id` и бизнес-связи **не изменяются**, история описывает только layout.

## B. Бизнес и сервисы

**AH-ACC-004 — capability и process**

Дано: capability «Управление персоналом», процессы «Приём сотрудника» и «Обновление данных» и IS «1С ЗУП».  
Когда: открыть бизнес-представление.  
Тогда: различимы capability, process, связь поддержки ИС; одна ИС может принадлежать нескольким процессам и категориям без дубликата.

**AH-ACC-005 — владелец и статус**

Дано: IS с owner, lifecycle, criticality и результатом функциональной/технической оценки.  
Когда: открыть паспорт.  
Тогда: корректно отображается, кто подтверждал сведения и когда; статус `active` не означает автоматически `verified`.

## C. Интеграционные потоки и данные

**AH-ACC-006 — один transport, два бизнес-контекста**

Дано: один Flow «1С ЗУП → ЕИБД», 60 каталогизированных атрибутов; контекст БП A использует 15, БП B — 9 (пересечение допустимо).  
Когда: открыть flow, затем выбрать БП A/B.  
Тогда: общий набор 60, по контексту 15/9; техническая стрелка и flow ID остаются одними; нет ложного задвоения.

**AH-ACC-007 — разные независимые направления**

Дано: поток A→B и поток B→A с разными портами/атрибутами.  
Когда: выбрать, сгруппировать, раскрыть и перетянуть конечную точку только одной стрелки.  
Тогда: исходные flow ID и атрибуты других потоков сохранены; изменение фиксируется в аудите после подтверждения.

**AH-ACC-008 — неизвестный маршрут**

Дано: flow с протоколом HTTPS/443, без подтверждённого FW-пути.  
Когда: открыть вкладку сетевого маршрута.  
Тогда: UI пишет `маршрут не подтверждён`, а не `маршрут разрешён`; может показать предполагаемый маршрут с пометкой и источником.

## D. Инфраструктура и сеть

**AH-ACC-009 — VRF-контекст**

Дано: два VRF, в каждом префикс 10.1.0.0/24.  
Когда: импортировать обе записи и посмотреть NIC/подсеть.  
Тогда: нет ложного конфликта IP в разных VRF; ID префиксов разные и соответствуют scope.

**AH-ACC-010 — VLAN vs VRF vs Zone**

Дано: VLAN 3111 внутри заданного scope, VRF `int-web`, зона DMZ, VM и NIC.  
Когда: представить их на холсте и переместить сетевые прямоугольники.  
Тогда: зона, VLAN и VRF остаются разными типами; членство интерфейса меняется только отдельной подтверждённой операцией.

## E. Управление и безопасность

**AH-ACC-011 — статусы достоверности**

Дано: 10 обязательных полей и конфликт из двух источников о VLAN.  
Когда: открыть quality report.  
Тогда: полнота, процент verified, свежесть, конфликты показаны раздельно; статус источника и доказательства видны, конфликт не скрыт автоматическим перезаписыванием.

**AH-ACC-012 — RBAC**

Дано: роли admin, architect, engineer, security, business_owner, viewer.  
Когда: повторить операции чтения/записи в UI и напрямую через API.  
Тогда: viewer не меняет архитектуру; право на изменение сети не даёт автоматически право на изменение бизнес-процессов; ошибки 401/403 понятны.

**AH-ACC-013 — изменение и аудит**

Дано: сохранённая IS и flow.  
Когда: создать черновик смены получателя, изменить порт, отменить часть действий, затем подтвердить.  
Тогда: preview показывает before/after и причины, flow ID сохраняется, audit фиксирует фактический commit, отказ не приводит к частичным данным.

**AH-ACC-014 — impact analysis**

Дано: подтверждённые зависимости IS → component → VM → service → process и отдельные предположения.  
Когда: запустить impact для вывода VM из эксплуатации.  
Тогда: список затронутых ИС/процессов объяснён цепочками; риски и предположения маркированы; `нет сведений` не равно `нет влияния`.

## F. Интерфейс и эксплуатация

**AH-ACC-015 — UX обычного пользователя**

Дано: карта из 8–30 ИС и десятков VM, несколько слоёв и групп потоков.  
Когда: впервые открыть на desktop и мобильном экране, выделить IS и её ближайшие зависимости, открыть свойства, закрыть Esc, включить Fit.  
Тогда: объекты читаемы, холст не закрыт панелью, нет бесконечного автоматического масштабирования, состояние выбора восстановимо.

**AH-ACC-016 — версионирование релиза**

Дано: фронтенд новой версии и backend со старой схемой.  
Когда: пользователь пытается открыть функциональность, требующую новую миграцию.  
Тогда: эта функция недоступна с объяснением, существующие экраны не падают; release pipeline не объявляет деплой успешным до health/schema/smoke проверок.

## Правило тестовой базы

- Тестовые объекты `QA-WORK-*` создаются изолированно и очищаются после прогонов.
- Тесты никогда не трогают продуктивные сведения без отдельного разрешения.
- Для каждого дефекта есть воспроизводящий сценарий, регрессионный тест и способ подтверждения.
- После изменения критичного API запускается корректная миграция пустой БД и существующей копии БД.
- Проверка браузера включает не только наличие элемента в DOM, но и реальное сохранение/повторное открытие.

## Отношение к существующим тестам

Сценарии **дополняют**, а не отменяют уже существующие Playwright- и backend-тесты. При разработке сверять `frontend/e2e/`, `backend/tests/` и CI GitHub Actions; не объявлять поддержку функции только по тексту документации.

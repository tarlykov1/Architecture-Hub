# Технические решения — контракт рабочего пространства (AH-02 / AH-05)

Обновление: **21.11.2026**. Функции ниже относятся к рабочей ветке [PR #212](https://github.com/tarlykov1/Architecture-Hub/pull/212). До её включения в `main` они не являются возможностями опубликованной версии.

## Назначение

Техническое решение позволяет проектировать изменения в ИТ-архитектуре, обсуждать и согласовывать их, **не изменяя** действующие ИС, ВМ, сетевые сегменты и потоки в реестре.

Публикация технического решения — публикация **документа**; она не означает внедрение. Фактические изменения инфраструктуры/CMDB выполняются отдельно с проверкой и аудитом.

## Модель и источники истины

| Сущность | Где хранится | Разрешённые действия |
|---|---|---|
| Действующая ИС / ВМ | `objects` / `infrastructure_items` | Просмотр в проекте, изменение только через основной реестр |
| Действующий поток | `data_flows` | Просмотр и выбор контекста, запись через основной реестр |
| Проектируемая ВМ/сервер/хост | `technical_decisions.proposed_vms` (JSON) | Добавить, выбрать, переместить, изменить свойства, удалить |
| Проектируемый поток | `technical_decisions.proposed_flows` (JSON) | Создать мышью или формой, изменить параметры, направление и концы, удалить |
| Маршрут согласования | `required_services` | Выбрать согласующие службы в черновике |
| Голос / комментарий | `technical_decision_reviews` / `technical_decision_comments` | Персональное согласование, замечания к решению, ВМ и потокам |
| История редактора | Локальный стек пользователя + серверные ревизии и аудит | Отменить/повторить последнюю записанную правку черновика |

**Идентификаторы:** при изменении положения ВМ и параметров существующего *проектируемого* потока ID сохраняется. Обратное направление не переписывает другие потоки.

**Точки соединения:** 8 точек на объект; отдельные `source_handle` и `target_handle`, направление и привязка к концам потока. Новые реальные потоки не создаются в момент рисования проектной стрелки.

## Операции редактора

1. **Добавить ВМ:** имя, тип (`vm/server/host`), среда, описание. Сохранение только внутри проекта.
2. **Переместить ВМ:** перетаскивание проектного узла; позиция сохраняется через `PUT /api/technical-decisions/{id}` с `expected_revision`. Действующие узлы заблокированы от перемещения.
3. **Открыть карточку ВМ:** клик/контекстное меню. Проектную ВМ можно переименовать, изменить тип, среду и описание. У действующей ВМ карточка только для просмотра.
4. **Удалить проектную ВМ:** явное подтверждение и количество затронутых проектных потоков. Удаляются только проектная ВМ и связанные с ней **проектные** потоки.
5. **Создать поток:** протянуть соединение от одной точки до другой или выбрать источник/получателя. Указать имя, протокол, порт, данные, защиту, периодичность и достоверность.
6. **Изменить поток:** выбрать проектный поток; свойства сохраняются целиком как одна ревизия. Разворот направления не создаёт второго потока.
7. **Отмена/повтор:** до 40 пользовательских изменений по снимкам проектных ВМ и потоков. Каждый откат записывается как новая серверная ревизия, чтобы аудит оставался целостным. Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, Ctrl+Y работают вне полей ввода; текстовые поля сохраняют обычное поведение клавиш.
8. **Несохранённая форма:** переключение редактора/вкладки/закрытие требует подтверждения, если локально изменены поля.
9. **Меню правой кнопки:** открыть карточку; удалить разрешённые проектные объекты/потоки; действия с действующими объектами не предлагаются.
10. **Вкладка «Изменения»:** явный список добавленных ВМ и потоков и параметров с напоминанием, что изменения не внедрены. Пока не является полноценным сравнением правок/удалений действующих объектов.
11. **Скачать документ (.md):** локальная Markdown-выгрузка текущей ревизии, включая участников, проектные ВМ/потоки, данные, защиту, согласования и замечания. **Это снимок**, не отдельная редактируемая версия архитектуры.

## Контроль целостности

`_decision_current_baseline` создаёт fingerprint важных элементов выбранной ИС: связанных компонентов, одного шага потоков, интерфейсов, IP, VRF/VLAN/зон, заявленных сетевых маршрутов, справочника и привязок передаваемых атрибутов. Не связанные с проектом сетевые записи не должны приводить к ложным конфликтам.

Если база изменилась после отправки на согласование, публикация блокируется до повторного рассмотрения. Этот контроль — **сравнение зарегистрированных данных**, а не независимое обнаружение сетевого трафика.

Ошибки конкурентного редактирования (`409`) не затирают чужую ревизию. Пользователь может обновить карточку и повторить действие на новой базе.

## Согласование

- `draft → in_review`; при замечаниях `changes_requested`, после доработки — новая версия и новый маршрут голосов.
- `approved` только после всех обязательных персональных согласований, автор не согласует собственное решение.
- `published` — согласованный документ без изменения реестров и сетевого оборудования.
- Анонимный доступ к просмотру/черновикам не равен праву электронной подписи; согласование требует персональной учётной записи.

## Проверки

Изолированная тестовая база; названия `QA-WORK-*`.

- API: `test_decision_proposal_metadata.py`, `test_decision_baseline_scope.py`, `test_decision_withdraw.py`.
- Playwright: `technical-decision-vm-layout.spec.ts`, `technical-decision-full-edit.spec.ts`, `decisions-workspace.spec.ts`.
- Приёмка должна проверять запись в API после реального drag, reload, undo/redo, привязанные потоки, отказ от удаления, неизменность действующей инфраструктуры и отсутствие подписей без персонального входа.

## Осталось в последующих очередях

Это **не полная реализация** AH-02/AH-05. Следующая очередь — единое ядро канвы со всеми режимами и топологией сетей; изменение/удаление *существующих* объектов как отдельный сценарий проекта, multi-IS и сеть; серверные baseline / visual diff «было–стало» для таких изменений; полное внедрение с контролем исходного реестра. Не выдавать простой список новых объектов за полноценный versioned diff.

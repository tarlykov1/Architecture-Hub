# Architecture Hub: безопасный preflight перед публикацией test.web-tie.ru

**Статус:** только подготовка. Этот документ и `scripts/preflight_test_release.sh` **не публикуют** приложение, не объединяют PR и не запускают Alembic на рабочей базе.

## Почему нельзя просто объединить PR и ждать автодеплоя

- В текущей `main` `deploy-test.yml` публикует **только frontend**, если задана переменная `DEPLOY_ENABLED=true`; он не обновляет API или SQLite.
- `deploy-backend-test.yml` управляется отдельным флагом `BACKEND_DEPLOY_ENABLED=true`. Он использует ограниченный root-owned `/usr/local/sbin/architecture-hub-deploy-backend` и вначале делает SQLite snapshot.
- **Этот PR изменяет порядок запуска:** CI успешного push в `main` → успешный backend deploy → только затем frontend deploy **точно той же ревизии**, которую backend передаёт через артефакт `backend-release-revision`. Для frontend теперь требуются **оба флага** `BACKEND_DEPLOY_ENABLED=true` и `DEPLOY_ENABLED=true`. При неуспешном backend-deploy frontend не публикуется. Каждый workflow дополнительно проверяет, что `main` не продвинулся дальше проверенной ревизии.
- Backend deploy запускает `alembic upgrade head` **только** при наличии файла `/etc/architecture-hub-enable-migrations`; иначе выдаёт успешное обновление кода без миграции. Новый API при этом может обратиться к отсутствующему столбцу `revision`.
- **Без изменения цепочки** frontend/backend workflow стартовали от одного CI независимо. В PR устранена эта гонка; но без проверки текущей серверной БД даже последовательный деплой нельзя считать безопасным.

Важное техническое ограничение GitHub Actions: при событии `workflow_run` собственный `GITHUB_SHA` вторичного workflow относится к ветке по умолчанию, **не обязательно к первоначальному CI-коммиту**. Поэтому frontend не использует его вслепую: backend записывает подтверждённый CI SHA в артефакт, а frontend загружает артефакт по ID завершившегося backend workflow, сверяет его с `main` и только затем делает checkout и сборку.

## Что проверено в репозитории

PR #161 (первая очередь), #162 (миграция 0013) и #163 (миграция 0014) успешно прошли отдельные CI. Эти прогоны используют **новую пустую SQLite** – они **не доказывают** готовность существующей серверной БД.

Целевая цепочка: `0010_auth_users → 0011_architecture_layer_regions → 0012_layer_region_opacity → 0013_logical_relation_unique → 0014_layer_region_revisions`. Миграция 0013 остановится, если есть исторические дубли активных логических связей; удаление не автоматизировано.

## Один безопасный запуск на VPS от root

Команды ниже загружают скрипт из проверяемого GitHub-коммита и **только создают консистентную резервную копию + читают метаданные базы**. Скрипт не выводит содержимое паспортов, пароли, адреса или токены.

```bash
curl -fsSL https://raw.githubusercontent.com/tarlykov1/Architecture-Hub/b9414b012b51dc5978f69ed08a9994085f55c887/scripts/preflight_test_release.sh \
  -o /root/archhub-test-release-preflight.sh
bash -n /root/archhub-test-release-preflight.sh
bash /root/archhub-test-release-preflight.sh
```

Скрипт проверяет сервис `architecture-hub.service`, путь `/opt/architecture-hub/backend`, пользователя/файл SQLite `/var/lib/architecture-hub/architecture_hub.db`, состояние Alembic, дубли активных связей, наличие контролируемого deploy-скрипта и opt-in миграций. Сначала делает online backup методом `sqlite3.Connection.backup` в `/var/backups/architecture-hub/release-preflight-*/architecture_hub.db`, затем проверяет его `PRAGMA integrity_check` и выполняет SQL-проверки **на копии**.

В случае `BLOCKED:` **не** создавайте файл разрешения миграций вручную, не выполняйте `alembic stamp` на рабочей базе и не запускайте публикацию: причину нужно проанализировать по выведенным кодам/статусу.

## Что должно быть известно перед разрешением merge/deploy

1. Вывод `READY_FOR_TEST_RELEASE_PRECHECK=1`; путь и целостность резервной копии подтверждены.
2. Текущая ревизия Alembic известна и соответствует реальной схеме; миграции `0011–0014` проверены **на восстановленной копии именно серверной БД**, а не только на CI-фикстуре.
3. У deployment-user работает ограниченный sudo-скрипт, **оба** флага `BACKEND_DEPLOY_ENABLED` / `DEPLOY_ENABLED` сверены и права сервиса/venv соответствуют фактическому окружению. Перед разрешением main push сначала должен быть объединён этот preflight/workflow PR с новым порядком публикации.
4. Публикация backend завершилась успешно, обновлённая API-модель поддерживает `GET/PUT /api/diagrams/layer-regions`, аудит и ревизии.
5. **Только после этого** публикуется frontend проверенного коммита; проверяется `build-info.json`, `/api/health`, UI авторизации и сценарии редактирования ВМ/потоков/слоёв.

**Не подменяйте** эти пункты выводом «CI зелёный»: успешная сборка не говорит об идентичности миграций сервера.

## Проверка после выкладки

Использовать реальные пользовательские сценарии: сессия администратора и наблюдателя, выделение ИС из реестра потоков, перемещение конкретной ВМ с повторным открытием, переподключение одного потока без изменения соседних, история, создание/редактирование области, сохранение цвета/opacity/geometry, конфликт ревизий, VRF/VLAN, мобильная версия. Не создавать в рабочей базе тестовые объекты без необходимости; если требуются, префикс `QA-WORK-` и учёт удаления.

## Ограничение текущего доступа

В обычном чате есть подключённый GitHub, но **нет интерактивного SSH-доступа к VPS и инструмента запуска серверных команд**. Поэтому шаги с SQLite на реальном сервере нельзя утверждать выполненными без фактического журнала preflight. Не выполнять последовательное слияние PR #161/162/163, если эти предварительные условия не подтверждены.
